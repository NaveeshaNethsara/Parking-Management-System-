Parking Management SystemProject Planning and Requirements Analysis1. Project OverviewThe proposed project is a Parking Management System, developed as a standalone Java application for managing the daily operations of a parking facility.The system will help parking staff manage vehicles, parking spaces, parking records, parking tickets, and payments through a simple graphical user interface.The application will be developed using Object-Oriented Programming (OOP) principles in Java. The project will specifically demonstrate important OOP concepts including:Classes and objectsEncapsulationInheritancePolymorphismAbstractionAssociation and object relationshipsEvent handlingCRUD operationsException handling and validationThe system is selected because parking management is a realistic problem domain with clearly identifiable real-world objects and processes. It also provides sufficient opportunities to demonstrate OOP concepts without introducing unnecessary complexity.2. SDLC Phase 1 — Planning2.1 Project GoalThe main goal of the project is to develop a user-friendly standalone Parking Management System that allows parking staff to efficiently manage parking operations.The system should replace or reduce manual processes such as recording vehicle information, assigning parking spaces, calculating parking charges, and maintaining payment records.The application should be simple enough for staff to operate while demonstrating strong object-oriented design and implementation.2.2 Project ObjectivesThe main objectives are:To develop a standalone Parking Management System using Java.To apply object-oriented programming principles in a real-world application.To manage vehicle information efficiently.To manage parking slots and their availability.To record vehicle entry and exit information.To generate and manage parking tickets.To calculate parking charges based on parking duration and vehicle type.To record and manage payments.To provide CRUD operations for relevant system data.To provide validation and error handling.To provide a simple and understandable graphical user interface.To test the application thoroughly before final submission.To provide documentation explaining the system architecture, design and OOP implementation.3. Problem Identification3.1 Existing ProblemTraditional or manually managed parking facilities may rely on paper records or basic manual processes to track vehicles and parking spaces.This can create several problems:Difficulty identifying available parking spaces.Time-consuming vehicle registration.Errors when recording vehicle entry and exit times.Difficulty calculating parking fees accurately.Difficulty maintaining payment records.Difficulty searching previous parking records.Risk of duplicate or incorrect records.Lack of a centralized way to manage parking information.A computerized Parking Management System can organize these activities within a single application.4. Proposed SolutionThe proposed solution is a standalone Java application that provides a centralized system for managing parking operations.The basic workflow will be:Vehicle Arrival↓Register/Search Vehicle↓Check Available Parking Slot↓Assign Parking Slot↓Generate Parking Ticket↓Vehicle Remains Parked↓Vehicle Exit↓Calculate Parking Fee↓Record Payment↓Release Parking SlotThis workflow represents the main business process of the application.5. Project Scope5.1 In ScopeThe first version of the system will include:Vehicle ManagementAdd vehicleView vehiclesSearch vehicleUpdate vehicle detailsDelete vehicleIdentify vehicle typeDisplay vehicle parking statusParking Slot ManagementAdd parking slotsView parking slotsUpdate parking slot informationDelete parking slotsDisplay available slotsDisplay occupied slotsAssign a slot to a vehicleRelease a slot when a vehicle exitsParking ManagementRecord vehicle entryAssign parking slotGenerate parking ticketRecord parking timeRecord vehicle exitCalculate parking durationCalculate parking feePayment ManagementRecord paymentView payment recordsDisplay payment amountDisplay payment methodAssociate payment with a parking recordDashboardThe dashboard can display information such as:Total parking slotsAvailable slotsOccupied slotsCurrently parked vehiclesTotal parking recordsTotal revenueValidation and Error HandlingThe system should handle situations such as:Empty required fieldsInvalid vehicle numbersDuplicate vehicle recordsAttempting to park when no slots are availableInvalid parking slot selectionAttempting to release an already available slotInvalid payment informationInvalid numeric input5.2 Out of ScopeTo keep the coursework manageable, the following features will not be included in the initial version:Online parking reservationsMobile applicationsCloud deploymentReal-time IoT parking sensorsAutomatic number plate recognitionOnline payment gatewaysGPS integrationMulti-branch enterprise managementArtificial intelligenceComplex user authentication systems unless required laterReal-time hardware integrationThese features could be considered future enhancements but are not necessary for the core coursework.6. Target UsersThe primary user of the application will be:Parking Staff / AdministratorThe staff member will use the system to:Register and manage vehiclesManage parking slotsRecord vehicle entriesGenerate parking ticketsProcess vehicle exitsCalculate parking feesRecord paymentsView parking informationThe system is primarily designed for internal parking facility management rather than public customer use.7. Functional RequirementsFR-01 — Vehicle RegistrationThe system shall allow the user to register a vehicle by entering relevant vehicle information.Possible information includes:Vehicle numberOwner nameVehicle typeContact informationFR-02 — View Vehicle InformationThe system shall allow the user to view registered vehicles and their current parking status.FR-03 — Update Vehicle InformationThe system shall allow the user to modify existing vehicle information.FR-04 — Delete Vehicle InformationThe system shall allow the user to remove a vehicle record when appropriate.FR-05 — Search VehicleThe system shall allow the user to search for a vehicle using information such as the vehicle registration number.FR-06 — Parking Slot ManagementThe system shall allow parking staff to create, view, update and delete parking slot information.FR-07 — Display Slot AvailabilityThe system shall display whether parking slots are:AvailableOccupiedFR-08 — Assign Parking SlotThe system shall allow an available parking slot to be assigned to a vehicle.The system shall prevent an occupied slot from being assigned to another vehicle.FR-09 — Record Vehicle EntryThe system shall record the date and time when a vehicle enters the parking facility.FR-10 — Generate Parking TicketThe system shall generate a parking record/ticket containing relevant information such as:Ticket IDVehicle numberParking slotEntry date/timeFR-11 — Record Vehicle ExitThe system shall allow staff to process a vehicle leaving the parking facility.FR-12 — Calculate Parking DurationThe system shall calculate the duration for which the vehicle remained parked.FR-13 — Calculate Parking FeeThe system shall calculate the parking charge according to the configured parking rules.Different vehicle types may use different parking rates.FR-14 — Process PaymentThe system shall allow staff to record payment information for completed parking transactions.FR-15 — Release Parking SlotAfter a vehicle exits, its assigned parking slot shall be changed back to an available state.FR-16 — View Parking RecordsThe system shall allow staff to view existing and completed parking records.FR-17 — Dashboard InformationThe system shall display summary information about the current parking situation.FR-18 — Data ValidationThe system shall validate user input before processing or storing information.FR-19 — Error HandlingThe system shall provide meaningful error messages when invalid operations are attempted.8. Non-Functional RequirementsNFR-01 — UsabilityThe interface should be simple and understandable for parking staff with basic computer knowledge.NFR-02 — PerformanceThe application should respond quickly to normal user operations such as searching, adding, updating and deleting records.NFR-03 — ReliabilityThe system should maintain consistent parking information and prevent invalid parking operations.NFR-04 — MaintainabilityThe system should be structured using appropriate classes and separation of responsibilities so that future modifications can be made easily.NFR-05 — SecurityThe system should prevent unauthorized or invalid modification of application data where appropriate.NFR-06 — Error HandlingThe system should handle invalid user input without unexpectedly terminating the application.NFR-07 — PortabilityThe application should be capable of running on a computer environment that supports the required Java version.NFR-08 — Object-Oriented DesignThe application should demonstrate appropriate use of OOP concepts including encapsulation, inheritance, polymorphism and abstraction.9. Application of OOP ConceptsEncapsulationData belonging to objects will be kept private and accessed through appropriate methods.Example:Vehicle-------------------------- vehicleNumber- ownerName- vehicleType- status-------------------------+ getVehicleNumber()+ setVehicleNumber()+ getOwnerName()+ setOwnerName()This protects object data from inappropriate direct modification.InheritanceCommon vehicle properties and behavior can be defined in a parent Vehicle class.Specialized vehicle classes can inherit from it.Vehicle   |   +-- Car   +-- Motorcycle   +-- VanPolymorphismDifferent vehicle types can provide different implementations of operations such as parking fee calculation.For example:Vehicle    calculateParkingFee()Car    calculateParkingFee()Motorcycle    calculateParkingFee()Van    calculateParkingFee()The appropriate implementation can be selected according to the actual vehicle object.AbstractionCommon behavior can be defined at an abstract level while allowing specialized classes to provide their own implementations.The exact use of abstract classes/interfaces will be determined during the design phase.12.
